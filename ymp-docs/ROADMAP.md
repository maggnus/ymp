# Roadmap

The roadmap has three product milestones: **POC → MVP → Alpha**. It is an evidence sequence, not a
percentage-complete schedule. Each statement below distinguishes implemented foundations,
designed behaviour, and behaviour not yet tested.

Current execution state lives under [work/](work/); [work/WAVES.md](work/WAVES.md) and
[work/STATUS.md](work/STATUS.md) are generated indexes, not product truth. The current scientific
decision is [RDR-002](research/rdr-002-cumulative-knowledge-poc.md).

## Current direction and supersession

ymp aims to accumulate provenance-bound knowledge across software tasks and determine whether a
frozen memory transfers to genuinely new tasks. The nearest visible product outcome is a coherent
chat-first terminal experience based on the approved [user journey](USER_JOURNEY.md). Product
quality and scientific validity are both required; neither substitutes for the other.

Same-budget superiority over a strong single agent or independent best-of-`n`, best-of-`11`, the
old 1,992-tasks-per-stratum threshold, and the mandatory weak-to-strong sequence are not current
delivery or POC-completion gates. Conflicting comparison passages retained in
[ARCHITECTURE.md](ARCHITECTURE.md), [PROTOCOL.md](PROTOCOL.md), and
[REPUTATION.md](REPUTATION.md) describe historical or separately approved later research and cannot
restore those gates. Frozen manifests, protocols, and results remain immutable history.

## Initial scope

The first empirical claim covers reproducible software repair and bounded code-change tasks. Each
live task requires a reviewed public specification, a prevalidated independent oracle, a pinned
toolchain and runtime profile, no production credentials, and no irreversible external action.
Source and target tasks, memory snapshots, conditions, observations, exact sample, limits, stopping
rule, and decision rule are frozen before collection.

During POC, every product or external-agent execution occurs in a newly created disposable
environment with isolated project, home, ymp state, temporary, build, and export paths. The POC
makes no product-security or hostile-code-containment claim. Arbitrary repositories, real
credentials, production deployment, and irreversible actions are outside scope.

## POC — bounded proof of concept

The POC is the first production version with a bounded feature set, not a disposable
implementation. It is delivered as one `ymp` executable whose public surface is a foreground
Ratatui application. The trusted kernel preserves finite authority, immutable candidates,
provenance, honest terminal states, and independent verification.

The POC is complete only after both of these outcomes exist:

1. the main terminal path coherently connects an ordinary goal to progress, evidence, revision,
   and explicit application without exposing internal protocol ceremony; and
2. valid empirical evidence supports a positive, negative, or inconclusive cumulative-transfer
   conclusion for an exact frozen regime.

An inconclusive conclusion still requires valid observations that fail to distinguish the
predeclared outcomes. Infrastructure failures alone do not close the POC.

### POC-0 — implemented production foundation

Implemented components include one executable, a foreground TUI, a typed application core, one
trusted writer, a digest-linked journal, content-addressed objects, isolated attempt workspaces,
immutable candidate ancestry, Codex and Claude Code runtime drivers, bounded lifecycle control,
task-scoped inert collaboration records, protected verifier evidence, and export paths.

These components provide mechanisms, not the current product or scientific result. Their accepted
tests remain valid evidence for their own contracts. They do not prove a coherent user journey,
cumulative memory, transfer, collective benefit, or containment of hostile code.

### POC-1 — first visible outcome: coherent terminal experience

Build the approved chat-first composition around real application projections:

- preserve the person's original goal and ask at most one materially blocking question;
- show preparation and work as concise progress inside the conversation;
- keep participant, pool, board, artifact, and protocol details optional and factually separated;
- distinguish automatic verification, human evaluation, unverified remainder, and infrastructure
  failure;
- provide an exact external command or path for the result, accept feedback as a revision, and
  require an explicit decision before applying exact bytes; and
- show unavailable state as unavailable rather than inventing data.

The current system-centred TUI does not yet satisfy this outcome. A polished transcript without a
working, independently checked candidate also fails it.

### POC-2 — executable cumulative-memory preparation

Before any new model expenditure:

- select the smallest supported memory carrier after inspecting existing facilities;
- define candidate-knowledge provenance and successive frozen snapshot semantics;
- freeze source and genuinely new target tasks, leakage rules, controls, profiles, observations,
  exact sample, limits, stopping rule, and decision rule;
- prepare experience-derived, no-memory, similarly sized generic-memory, and any predeclared
  disjoint or irrelevant-memory conditions; and
- use a deterministic runtime to demonstrate digest binding, provenance, condition assignment,
  protected-input separation, promised instrumentation, cost/outcome capture, and honest failure.

Read-back or echo proves byte access only. A participant may validly decline to read available
memory. Missing promised instrumentation is a distinct invalid observation. Every infrastructure
failure remains in cost and outcome logs and is never recoded as a failed solution or negative
transfer.

This preparation approves no live task pair, corpus reuse, representation, sample, budget, or
profile by itself. Those choices require the frozen executable package and fresh authorization.

### POC-3 — accumulation and genuinely new-task transfer

After authorization, the empirical sequence proceeds in increasing claim strength:

1. a bounded source-task → target-task carrier probe establishes delivery and observability but
   cannot close the cumulative POC;
2. successive source tasks create frozen memory snapshots with retained, revised, or superseded
   items and exact provenance;
3. genuinely new target tasks compare the experience-derived memory with the frozen controls in
   fresh sessions of the same receiver profile; and
4. an independent verifier judges exact target candidates while all costs, exclusions,
   infrastructure failures, abstentions, and uncertainty remain visible.

A positive cumulative result requires attributable knowledge from more than one earlier point and
favourable transfer under the predeclared rule. A valid no-benefit or harmful contrast supports a
bounded negative result; a harmful contrast, not a failed runtime, is negative transfer. Valid but
non-discriminating evidence supports an inconclusive result. A larger archive, fluent conversation,
fake-runtime success, old frozen study, or one carrier probe cannot close this stage.

Collective benefit is a later optional claim. It requires a control in which one agent with the
same receiver profile receives the exact same memory bytes. The current POC does not require
collective superiority.

## POC decision point

- **Positive:** accumulated memory transfers under the frozen rule; publish the exact supported
  regime and consider productizing that mechanism.
- **Negative:** valid evidence shows no useful transfer or shows harm; publish the bounded result
  and do not claim the mechanism works in that regime.
- **Inconclusive:** valid evidence cannot distinguish the predeclared outcomes; publish why and
  decide explicitly whether another bounded study is justified.
- **Invalid:** runtime, isolation, digest, candidate, oracle, or evidence integrity was lost; retain
  the event and cost, repair the preparation, and collect no scientific conclusion from it.

None of these conclusions authorizes use on sensitive repositories, product credentials,
irreversible external actions, or a claim of general intelligence.

## MVP — dependable local product

MVP turns supported POC behaviour into a dependable local product without broadening the empirical
claim. Its exact scope is chosen after the POC conclusion; a negative or inconclusive research
result does not become a positive mechanism claim through product polish.

Candidate MVP work includes:

- a verified strict Linux execution profile with private namespaces and filesystems, cgroup
  control, syscall and network restrictions, credential brokering, and descendant cleanup;
- stronger verifier isolation, bounded protected feedback, and exact provenance;
- dependable pause, cancellation, recovery or explicit crash termination, cleanup, upgrades, and
  evidence export;
- complete enforcement of participant, parallelism, time, money, communication, and verification
  limits; and
- the same coherent terminal path over supported runtimes and task classes.

MVP remains one executable and a foreground local application. A background daemon, operator
network service, cluster, arbitrary-project support, and silent fallback to weaker isolation remain
outside this milestone.

## Alpha — limited external trial

Alpha distributes the supported MVP to a small set of consenting users and held-out repositories.
It separately evaluates interface usefulness, cumulative-transfer behaviour, safety, compatibility,
false acceptance, cost, latency, infrastructure failure, and abstention. Presentation cannot mask
a negative or inconclusive mechanism result.

Alpha requires:

- no unresolved critical containment, state-integrity, cross-attempt, or verifier-boundary defect;
- reproducible package, migration or explicit crash-termination, cleanup, and export behaviour on
  supported hosts;
- exact compatibility windows for supported runtime and model routes; and
- explicit rejection of unsupported repositories, routes, platforms, and authority requests.

Another project class, external action, platform profile, or collective-benefit claim requires a
new threat analysis, frozen contract, and held-out evaluation.

## Later optional modes

A client/server, web, or cluster mode is not a POC, MVP, or Alpha criterion. Any later mode must
reuse the same domain commands, authority rules, immutable objects, event semantics, and independent
verification. It needs its own network, multi-client, storage, failover, identity, and partition
threat model. It is rejected if it introduces semantic central scheduling, treats MCP as the
authoritative internal protocol, or makes an external service necessary for local TUI use.

## Definition of done for the bounded POC

- the coherent terminal path is demonstrated against real application state and rejects fabricated
  values or internal ceremony as success;
- the exact supported task, memory, receiver, runtime, and oracle regime is published;
- cumulative-memory provenance, target separation, controls, promised observations, and honest
  terminals are executable and frozen before live collection;
- valid empirical evidence supports the stated positive, negative, or inconclusive conclusion;
- false acceptance, infrastructure failure, cost, latency, abstention, exclusions, and uncertainty
  are reported rather than hidden;
- no known check bypasses subject-bound authority, private workspaces, candidate immutability,
  protected verifier separation, or finite resources; and
- release packaging contains one `ymp` executable and no hidden dependency on Paseo or another
  orchestrator.

This definition never justifies “accepted results on arbitrary projects”, general collective
intelligence, or same-budget superiority.
