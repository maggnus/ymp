# Incremental knowledge and checked experience

YMP-113 builds on the existing memory table, FTS5 index and YMP-117 result journal. It adds no separate truth database and no model call to retain or retrieve a checked outcome.

When memory is enabled, after each accepted task the runtime immediately retains a project outcome projection and then asks the configured proposal policy for optional additions. Both the entry and its `knowledge_retained` event commit in one transaction. This happens before later siblings, reputation attribution and optional final learning. A failed proposal policy leaves the project outcome intact. Retaining the same source/proposal/applicability tuple again is idempotent and cannot reactivate a retired entry.

A confirmed project projection contains only the actual checked criteria and captured artifact identities, with at most 4,000 Unicode characters from each text artifact. It does not turn an executor's report or a reviewer's lesson into a confirmed assertion. A fully confirmed source can also support bounded shared experience describing the declared check types with actually observed passing evidence: exact bytes, actual input comparison, or a pinned validator. Shared text contains no project paths, artifact bytes, names, dataset values or freely generalized lesson. Its confirmation concerns the recorded source run and its declared criteria.

Accepted results without full confirmation retain a project candidate, including the unconfirmed result report. Partial passing evidence remains linked but does not activate the whole result. Free-text proposal-policy output, reviewer lessons, `memory_propose` findings and optional final learning remain explicitly unconfirmed candidates even if another agent agrees. Optional extraction persists its candidate before asking for review, so a later review failure cannot erase it. No knowledge path awards reputation; YMP-117 remains the only competence-credit consumer.

## Source and lifecycle contracts

`MemoryEntry.provenance` adds confirmation, exact-match applicability constraints, an optional `KnowledgeSource`, origin assignment/invocation IDs and the proposal implementation ID/version. The source names the actual acceptance record, result ID/version, criteria version and confirmation decision IDs. Runtime projections refer to the original producing assignment; policy-written candidate content is attributed to the policy, with the accepted result retained as context rather than an assertion that its producer wrote the candidate. Team-tool and optional-learning candidates retain their actual producing assignment/invocation.

Historical entries deserialize with absent provenance, meaning unknown confirmation. Their stored lifecycle values are preserved for inspection. They do not enter supported automatic context and are never upgraded by an agent's approval. New confirmed entries require `Store.retain_knowledge`; ordinary saves cannot install confirmed provenance, alter evidence-linked content or replace a protected record with a legacy-shaped record. `forget_memory` retires a record without deleting its source history.

`Store.memory_inventory(project)` returns stored lifecycle snapshots across statuses. Its recorded confirmation is historical; callers must not treat it as proof of present source freshness. `Store.resolve_memory(project, id, version, scope, mode)` checks present availability. It loads the actual stored entry, validates an optional serialized-record digest, checks project/global scope and every supplied applicability constraint, and resolves the acceptance/result/evidence through the existing journal. Changed artifacts, changed supplied inputs, stale result bindings, wrong versions, retired entries and unknown sources cannot enter supported context. An absent applicability key does not match. Global scope does not waive evidence freshness or explicit applicability.

`Store.search_memory` has two typed modes: `Supported` is the default used by `Store.memory` and automatic context; `IncludeUnconfirmed` is an explicit inspection choice for candidates and historical unknown entries. Inspection still enforces project/applicability and retirement constraints and labels confirmation in assembled prompts. `memory_search` exposes `include_unconfirmed` for a team member to inspect candidates; proposing and inspecting never activate them. Full inventory includes rejected and retired records for UI inspection.

YMP-114 can use the immutable source reference, retained lifecycle event, deterministic entry identity and existing `supersedes` field to implement correction. YMP-113 filters changed source versions but does not implement correction, semantic scope inference, cross-file source replacement or a general natural-language router.

## Replaceable policies and retrieval accounting

`Engine.knowledge_retrieval` and `Engine.knowledge_proposals` accept compiled implementations of narrow typed traits. They receive read-only inputs and return selected IDs/version hints or proposals, never a mutable store. The runtime always retains the accepted project outcome and owns activation, source resolution and context limits. A proposal policy can choose optional procedure projections and candidates; it cannot replace the source acceptance or supply arbitrary confirmed text.

The default retrieval implementation keeps SQLite FTS5 and the original effective query policy. An alternative can select from the project/global inventory instead. The runtime records the actual candidate source and selected implementation ID/version; inventory selection records a null effective FTS query. Policy output is re-resolved before context assembly, duplicates are omitted, and at most five actual excerpts consume a combined allowance of 8,000 Unicode characters including separators. The `memory_retrieval` event retains the actual source record version, included excerpt digest/count, confirmation, provenance, mode and applicability. Proposal-policy selection is also recorded even if the policy returns no additions or fails.

## Deterministic outcome inspection

`Store.outcomes(source_session)` returns typed accepted outcomes with the original directory, result ID/version, absolute captured artifact paths, digests, current confirmation and freshness. The directory resolves from the immutable producing assignment, captured task workspace or captured session policy, in that order; mutable project registration is never a historical location source. Freshness and confirmation inspect the same original directory. Relocating the project association does not move files or change a current outcome’s grade. If a legacy result has no captured absolute directory, the API returns `outcome_location_unknown` with its result/session identity instead of inventing a location. It starts no provider or production work and works for non-Git directories and sessions whose later tasks failed. Artifact paths come only from the existing captured result; outcomes without declared artifact snapshots do not acquire guessed locations. A caller can use the same API from the source or a later session. CLI/TUI location routing is an integration consumer of this API.
