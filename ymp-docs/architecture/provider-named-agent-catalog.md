# Provider-named agents from native discovery

Owner clarification, 2026-09-13: displayed agent names must come from Claude Code, Codex and other enabled systems after scanning their available offerings. Provider labels such as `Claude`, `Codex` and `GLM` are transport identities, not the selectable team members. Do not replace them with a hand-maintained list of model marketing names.

The implementation at task registration failed this requirement in two places. Default configuration created three provider-named profiles with no model. Native capability collection obtained model identifiers and controls, but dropped display names and did not populate the selectable pool. The owner's local configuration still contained those three placeholders. This is a product correction, tracked as YMP-127, not a change to the approved intent file.

Native scanning must preserve the exact returned identifiers, display names, aliases/resolved identifiers when supplied, and effort/control choices with their source and observation time. A returned identifier is the factual fallback when no separate display name is supplied. Missing metadata stays unknown; unavailable names or effort settings are not manufactured. Preserve provider-specific control names and values rather than assuming one universal effort ladder.

The discovered catalog must reach actual agent-pool and team selection, not only a diagnostics command. Names shown for an effective assignment must agree with its recorded native model/settings. Provider identity is a separate technical field. Stable local actor IDs, instructions/context, user pins, custom configuration and captured historical identities remain distinct from presentation metadata. Refreshing a catalog does not enroll every offering, rewrite historical sessions, duplicate actors or reset qualified experience merely because a timestamp changed.

Use the installed systems' metadata APIs with native authentication and no model prompts. Keep captured discovery/cache data under the application home. Manual capability claims must not become native observations. UI painting and ordinary inspection consume stored snapshots; scanning is an explicit bounded operation or necessary startup initialization, not a repeated paint-side probe. Legacy provider placeholders require a supported upgrade path to concrete discovered configurations or an explicit unresolved state, rather than remaining apparently real scanned agents.

YMP-127 verifies the complete path with native-protocol fixtures returning distinctive names, changing catalogs, partial failures, multiple agents from one provider, stable identity/pins/history, and model/effort overrides. A real metadata-only scan of the installed providers validates naming against their actual responses; no inference quota is implied. All UI work uses Claude Opus 5 max. The current provider-owned names must appear in the built executable after integration and supported local configuration refresh.

## Executable catalog contract

`ymp catalog` reads stored metadata and the selectable pool without launching providers. `ymp catalog --refresh` scans enabled native providers once each, saves the results, and reconciles concrete profiles. `--provider ID` limits the scan to one provider; `--timeout-secs N` sets a per-provider deadline between 1 and 60 seconds (default 30). At most 32 providers and 4,096 offerings per provider are accepted. Codex pagination is additionally capped at 32 pages. Concurrent scans are rejected before another provider starts. Configuration and scan locks explicitly release ownership when their guards end, even if a child temporarily retains an inherited descriptor; closing that stale descriptor must not release a replacement owner. Configuration publication is serialized, and an edit made during discovery rejects publication rather than overwriting the edit.

`ymp init` also performs this migration for an existing configuration. A fresh application home initializes metadata before its first interactive or headless team run. Existing homes can use `ymp init` or `ymp catalog --refresh`; ordinary inspection and terminal painting never trigger repeated scans. These operations send no user/model prompt. The Claude bridge must first be installed and built using its documented npm workflow.

Successful native observations live in `provider-catalog.json` under the selected application home (`~/.ymp2` by default). Each observation is bound to the provider kind, command, arguments and environment **reference names**, with its native method and observation time. No environment values or native stderr are retained. `config.toml` capability claims remain configured claims even when they contain a `native_metadata` source tag; they cannot supply native presentation names. Changing the provider command or its arguments invalidates the cached observation for that provider. A failed refresh retains its preceding applicable result and marks it stale; observations older than 24 hours are also displayed as stale. A provider without a successful snapshot remains unknown or unresolved. Retry a failed or interrupted publication with the same refresh command; no historical session is rewritten.

`ModelCapabilities` preserves the exact wire identifier, optional display name, native aliases and resolved model. A Codex picker row ID is recorded separately as `picker_id`: that ID alone is not evidence that the native wire accepts it as a model. Native controls retain their field names, choice values and supplied labels. ACP controls describe the current model; other advertised models retain unknown controls until a native observation supplies them. An observed default/current control value does not become a requested assignment effort.

Generated provider placeholders retain their actor IDs, enabled state and instructions. An explicit user model default or pin takes precedence during migration. When that policy already supplies a concrete model, the raw profile model stays unchanged: copying the same model into a previously empty profile field would change the execution-version key and disconnect qualified experience for unchanged execution. The scanned pool still resolves the concrete effective model and its native name. Otherwise migration selects the native default, or explicitly chooses and records the first returned offering when the provider has not named a default. Other offerings receive stable local actor IDs in the pool. Existing custom profiles remain separate, including two actors using the same model. Refresh never adds every offering to the configured starting team, alters team constraints, or merges actors. Removed offerings remain inspectable with unavailable or unknown model status according to the native list's completeness.

`Config::agent_identity(profile, effective_settings)` supplies the native name, original configured alias, exact requested model/effort, resolved model, source and an explicit native/stale/unknown/unresolved/local status. Pool projections and new runtime participant captures use this presentation. Each new assignment stores its identity for its effective settings in `AssignmentRecord.agent_identity`; older assignments without that field remain historical/unknown. Display names and observation timestamps are excluded from profile and execution-version hashes. A real model, instructions or native reported-settings change can still distinguish execution experience, as required by the execution contract.

## Verification

`cargo test -p ymp-cli --test native_catalog` executes scripted Codex and ACP native protocols through the real `ymp` binary. It covers distinctive native names, paginated offerings, controls, migration, actual selection, model overrides, repeated/changed/failed scans, deadlines, disabled/custom actors, pins, historical records, stale and provider-mismatched cache data, false TOML provenance, simultaneous refreshes and edits during a scan. Deterministic Unix descriptor-duplication controls cover both configuration and scan locks: the next owner can acquire while a stale descriptor remains open, and closing that descriptor leaves the new owner exclusive. Both controls fail with the original close-only release. First-migration regressions for both fixed and defaulted model policies first acquire an actual confirmed outcome, run the public executable scan, and verify that a fresh session finds the existing qualified experience through its real allocation lookup. Previously unknown execution still receives a distinct version when discovery selects a model. A positive prompt sentinel first proves that the fixture wire capture detects released model requests before asserting that catalog scans contain none.

After `npm ci && npm run build` in `ymp-bridges/claude`, run `cargo test -p ymp-cli --test native_catalog -- --include-ignored` to additionally exercise the real Claude SDK against its scripted native executable. That separate fixture check scans and selects Claude offerings without an installed-provider inference call. Bridge protocol tests also verify exact names and resolved aliases before any user message is released. Installed-provider metadata observations and regression-control results are recorded in [the YMP-127 backend evidence](../research/evidence/native-catalog-127.json).
