# YMP-132 independent backend review

**Accept corrected backend `dcaebd1cec392e94e3a4ea96a4831ee5b8a5bcad`. No remaining findings.** Reviewed the original `1e13650` implementation, `848e3b9` history filter and the follow-up correction. UI and full-release acceptance are outside this verdict.

One finding was identified and resolved. On `848e3b9`, `Engine::follow_up` saved the decoded user-visible answer using plain `post` at `engine.rs:553`. Its raw `conversation` message had an invocation origin, but the actual `answer` message did not. An independent public Engine run reproduced this with exactly one mock invocation: `raw_conversation_attributed=true`, `final_answer_attributed=false`, exit 101. The correction at [engine.rs:532](/tmp/ymp132-agent-attribution/ymp-rust/crates/ymp-runtime/src/engine.rs:532) retains `RecordedResponse` and saves both `answer`/`steer` responses through `invocation_message`. The unchanged independent probe now exits 0 with the final answer attributed and still exactly one invocation. The added in-tree regression also checks that raw and decoded messages name the same invocation.

The remaining implementation satisfies the reviewed boundaries:

- [attribution.rs:28](/tmp/ymp132-agent-attribution/ymp-rust/crates/ymp-core/src/attribution.rs:28) resolves exact assignment/invocation IDs within the trace's session and requires the assignment actor to match the message author. Requested, sent and reported settings come from that invocation; captured identity remains optional. It does not substitute the actor's newest invocation or current profile.
- [attribution.rs:52](/tmp/ymp132-agent-attribution/ymp-rust/crates/ymp-core/src/attribution.rs:52) reads both new origins and existing `TeamOperationCommitted.message_seq` links. Conflicting origins return unknown. Repeated identical origins remain stable; missing or incompatible linked records cannot supply an attribution. Streaming attribution requires one unambiguous running invocation for that actor.
- [storage/lib.rs:255](/tmp/ymp132-agent-attribution/ymp-rust/crates/ymp-storage/src/lib.rs:255) derives the author and assignment from a session-checked invocation. Message insertion, ordinary message event and origin event share one transaction. An independent SQLite trigger that aborts the origin insert demonstrated complete rollback: neither the message nor either event survived. Identity references are immutable through the normal storage transitions; their preliminary reads introduce no observed identity race.
- The new history filter checks the exact sequence before deserializing provenance, avoiding repeated copies of unrelated large assignment/result payloads. Attribution performs no additional SQL or discovery; persisting a response adds two indexed record reads and one event insert to the existing message transaction. No schema or `Message` field changes are required.

Independent checks passed: two storage regressions, the actual Engine response-origin test, the final corrected public follow-up probe, formatting, and scratch controls for insertion rollback, duplicate/conflicting origins, cross-session invocation, wrong assignment actor, missing assignment, ambiguous active work and unknown legacy identity. The retained old-runtime-post control fails at the intended missing-origin assertion. Source and log hashes are recorded in [review evidence](backend-review-evidence.json).

Limitations: historical runtime messages without either exact link remain unknown intentionally. Lookup still scans the in-memory history and record vectors; no large-transcript rendering benchmark or indexing claim was established. The unfinished UI must use these records correctly before the reported display issue can be considered closed. No reviewed source, user files, application home or native model was changed or invoked; only isolated scratch probes and reports were created.
