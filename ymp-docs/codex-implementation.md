# Codex protocol and execution boundary

Canonical status remains in `tasks/records/W1-0018.json`. CodexAppServer implements
NativeDiscovery and ExecutionBackend through the existing Registry, Gatekeeper
and execution host. Protocol conformance, native metadata and native model
inference are distinct evidence sources; the checks below do not establish an
empirical self-organization result.

## Selected protocol and observed version

The implementation targets the installed `codex-cli 0.156.1` App Server over
newline-delimited JSON-RPC on stdio. `codex app-server --help` confirms
`--listen stdio://` and the local schema-generation command. The experimental
surface is needed for explicit empty execution environments and dynamic file
tools. Authentication remains with Codex; ymp does not copy its credentials or
substitute a different native identity.

On 2026-09-28, schemas generated by this exact executable had these SHA-256
digests for `codex_app_server_protocol.v2.schemas.json`:

| Surface | Digest |
| --- | --- |
| Stable | `995fc3b8f8c469f6787e8fc5be4038c4f31359025edd8480b862e83355f3bf3b` |
| With `--experimental` | `a7225c28a57bd63b41470fde4cb18d80d75860e3e8533234473d64a01962740b` |

The local schema is the version-specific wire reference. The official
[App Server documentation](https://learn.chatgpt.com/docs/app-server) and
[configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference)
explain the protocol and settings, but a newer documented field does not establish
that this executable supports it. No legacy-tag source was consulted.

The following distinctions matter in this version:

- `Model.model` is the native model identifier; the catalog's `id` is a distinct
  field. Supported reasoning efforts and the default effort belong to each
  offering. Family is unknown unless actually supplied by an attributable source.
- `ThreadStartParams.environments: []` explicitly disables environment access for
  turns without an override. The adapter must also provide the empty selection
  on each turn, particularly after resuming a thread. Dynamic tools are an
  experimental API and need explicit capability opt-in.
- The local `readOnly` sandbox shape has `networkAccess` but no restricted
  readable-root field. It is not a substitute for the existing InvocationFiles
  mediator. `disabledPluginIds` explicitly does not yet filter plugin capabilities.
- Thread model/effort fields acknowledge saved configuration. They are not
  independent telemetry of the model that actually processed a particular turn.
- Usage contains `total` and `last`, with input, cached input, output, reasoning
  output and total-token fields. `cacheWriteInputTokens` has schema default zero;
  absence of other required counters does not mean zero. Reasoning is included
  in output, and cache reads/writes are included in total input.

## Metadata and environment observation

A bounded development probe used native authentication, configuration and model
metadata without a `turn/start` request or model inference. It found that sending
`mcp_servers={}` did not remove an inherited enabled server. Per-name
`enabled=false` overrides followed by effective-configuration inspection reduced
the enabled count to zero. Effective settings confirmed disabled shell tools,
code-mode host, apps, plugins, hooks and other configured external surfaces.
`unified_exec` still reported enabled despite the requested false value; this
observation is retained and must not be described as a successful disable.

Only after inspecting these effective restrictions, the probe created an
ephemeral thread in a disposable technical directory. The response confirmed
`environments: []`, `readOnly` with `networkAccess: false`, zero runtime workspace
roots, zero instruction sources and matching configured model. No task workspace
was passed to Codex. The native credential store was neither read into ymp state
nor copied.

One explicitly bounded `thread/shellCommand` request containing only `true`
returned an empty RPC acknowledgement. That user-initiated API is documented as
running outside the thread sandbox. This result does not prove exclusion of
model-facing tools and is not a model call. The adapter must not expose arbitrary
client RPC methods to an agent. The environment schema and acknowledged empty
selection define the supported mode; actual native model-tool behavior has not
been exercised by this probe.

## Reported usage basis

The exact upstream `rust-v0.156.1` implementation supplies the normal-completion
basis for interpreting reported usage. It records response token usage and emits
the token-count event before returning from sampling; task completion then emits
TurnComplete. App Server maps these to attributed usage and turn-completion
notifications. However, a response with absent token usage leaves the previous
counters unchanged; a later TokenCount can therefore repeat stale values. Event
ordering alone does not establish complete coverage. The adapter must require
fresh attributable final usage and preserve uncertainty when freshness is absent.
A later thread read can confirm the exact completed turn and idle state; that RPC
alone cannot invent a missing final usage guarantee. These are reported counters,
not an independent measurement of provider billing. Sources: [sampling and token counts](https://github.com/openai/codex/blob/rust-v0.156.1/codex-rs/core/src/session/turn.rs),
[missing-usage handling](https://github.com/openai/codex/blob/rust-v0.156.1/codex-rs/core/src/session/mod.rs),
[task completion](https://github.com/openai/codex/blob/rust-v0.156.1/codex-rs/core/src/tasks/mod.rs),
[App Server event mapping](https://github.com/openai/codex/blob/rust-v0.156.1/codex-rs/app-server/src/bespoke_event_handling.rs).

## Runtime consumer

The recorded adapter selection includes an explicit executable, Native or
ProtocolFixture source, a connection timeout up to 30 seconds and a frame limit
from 1 KiB to 1 MiB. Registry admission, workspace mediation, contribution
selection, verification-cost estimates and final reviewer selection use the same
specific mediated-backend guard. The Codex mode must match its version, selected
parameter digest and discovery source. Merely naming a native provider does not
grant execution authority. Scripted keeps its existing consumer path.

Only ReadFiles and WriteFiles can be granted to this adapter. Dynamic tools call
the original InvocationFiles interface, which checks current grants, physical
ownership and path scope. Codex receives a technical directory and an empty
environment selection, not the task's filesystem root. An assignment with no file
permissions has no file capability even when the provider advertises file-tool
availability. Command, network and browser capabilities are not provided here.

The transport uses bounded nonblocking pipes and deadline-limited writes. Startup
failures clean up their own process and technical directory. One adapter retains
at most 64 invocation identities; event, pending-notification and tool-call
collections have finite limits. An invocation identity is consumed before launch
and cannot be started twice. A repeated identical tool-call identity returns the
cached response; changed arguments under that identity are denied. A later legal
write cannot be overwritten by replaying an earlier successful call.

InvocationControl comes from the original host and checks live stop, grant and
clock before thread creation/resume and immediately before `turn/start`. The
invocation deadline is not reset after setup. File callbacks wait for the first
host event poll, after its start confirmation has been committed. This avoids a
startup revision race without blindly repeating file I/O. Stop, controller drop
and deadline end that wait. Other concurrent revision failures remain explicit
tool denials. Native progress text does not create checks or evidence; only the
bounded final agent message becomes the role response, once.

InvocationContinuation binds fresh admitted work and funding to one exact prior
completion. The kernel requires the same session, profile, provider and backend,
confirmed Completed work, closed file access and complete accounted usage. The
adapter also requires its retained local completed state and idle transport. It
resumes that same thread, rechecks effective restrictions, reapplies current
settings and grants access only through the new InvocationFiles. Losing that
local state makes reattachment unavailable. An uncertain previous call cannot be
restarted or continued. Absent continuation fields preserve old dispatch bytes.

Usage updates replace cumulative counters; they do not add duplicate totals or
add `last` to `total`. Continuation subtracts its exact known baseline. Complete
means complete reported usage under the supported, uninterrupted observed protocol
chain. Final stale updates, visible missing updates, retries, compaction,
ambiguous batches, resets and disconnects preserve Partial/Unknown. The protocol
cannot independently reveal an entirely invisible provider response or verify a
provider bill. Cancellation acknowledgement and process cleanup do not establish
complete cost. Task-file release depends on host-mediated withdrawal, separately
from financial settlement.

The final state read must identify the completed turn and an idle thread. A
transient still-active response currently yields a conservative failure rather
than a retry; this limitation does not justify fabricated completion. Unknown
model execution settings remain unknown: saved thread configuration is checked
for conflicts but is not copied into per-turn reported telemetry.

## Native run procedure

The standing authorization in AGENTS.md covers bounded development experiments.
The owner's engine-readiness direction still applies: product experiments start
through the completed accountable session, beginning with a homogeneous GPT team
and an elementary task. A protocol fixture or metadata probe is not that experiment.

Before a native run, use the implemented discovery consumer to capture the exact
executable/version, offerings and supported settings. Select an available GPT
model and supported low reasoning setting under the standing authorization,
recording uncertainty when comparable token-use evidence is unavailable. Fix the
resource limits and disposable task inputs before admission. Record the selected
backend policy, native version, requested/sent/reported settings, invocation and
native-session references, check results, expenses and unknown coverage.

Use fresh admitted work and reservations for continuation. A disconnect, parent
exit, interrupt acknowledgement or process-group cleanup cannot prove final
billing or authorize another start. Retain unresolved accounting. Task file
cessation follows the existing mediated-access withdrawal, independently of
native inference cessation. Never describe observed timeout or token counters as
a provider-enforced maximum billing cap.

The first process-fixture consumer passed in 19.64 seconds through actual
Registry, SQLite, Gatekeeper and ExecutionHost. It exercised a permitted mediated
write, denied path escape, repeated tool-call identity without repeated I/O and
a second newly admitted Planner continuing the same thread without file access.
Each invocation retained input 5, cache-read 2, cache-write 1, output 1 and
reasoning 1, with complete reported fixture usage and no remaining financial hold.
The second invocation subtracts the retained cumulative baseline. The fixture
sends a growing late usage update before the final thread-read response, not just
an identical duplicate. Native thread creation, resume and turn counts are checked
separately. These are synthetic protocol answers, not native model observations.

Short actual-consumer checks passed in 11.14 seconds for missing required response
identity, disconnect after observed usage, malformed late usage and stopping while
setup was paused. They retain uncertain reservations rather than claiming complete
usage or confirmed completion. The stopped setup sends zero `turn/start` requests;
duplicate start and unresolved recovery cannot create another call.

Removing the native pre-inference authority checks made the stop scenario fail
with one forbidden turn instead of zero (10.59 seconds). After restoring the
checks, all three protocol-consumer scenarios passed in 19.39 seconds. Discovery
and malformed-usage checks also passed independently in 1.40 seconds.

After the coverage refinements, the three process-consumer scenarios passed in
24.64 seconds. The explicitly selected metadata-only test then exercised this
Rust adapter against installed Codex on 2026-09-29 (Hong Kong): version 0.156.1,
seven discovered offerings and zero model turns, in 3.41 seconds. That test is
ignored in ordinary offline test runs and requires an explicit executable.

The final focused uncertainty checks passed in 21.67 seconds, the existing
accounted Scripted scenario in 7.95 seconds, and targeted Clippy and formatting
passed. Independent review of the stable source returned R1(9/10) ACCEPT.
The first combined-workspace run exposed an existing producer-capture/revocation
race through the report scenario: a transient failure before CaptureStarted left
the host permanently blocked. After the narrow host correction, the actual report
scenario passed in 36.55 and 37.18 seconds; its original 90-second wait limit was
not increased. The correction retains proof across failed reads and retries only
unstarted capture preparation, never completed I/O. Independent review of this

Clippy with denied warnings and all ordinary workspace tests. Both final-report
scenarios passed in that run (36.39 seconds). Task-register and diff checks passed.

The combined runs use `CARGO_PROFILE_TEST_OPT_LEVEL=1`, with debug assertions and
overflow checks explicitly enabled. `make verify` still runs every required

## Policy version 2: native Code Mode compatibility

The [first native pilot](experiments/homogeneous-gpt-elementary/README.md) later
exposed a compatibility failure in version 1. Its known thread's stored tool
items show an `exec` call attempting `tools.ymp_read`, followed by
`code-mode host is disabled`. The native process completed, but the kernel refused
the resulting error object as a plan. No file-tool result was fabricated.

In the pinned release, model metadata tool_mode takes precedence over
features.code_mode. CodeModeOnly cannot fall back to direct tools when the host
is unavailable. Therefore code_mode=false alone does not establish a direct-tool
mode. See the exact [mode selection](https://github.com/openai/codex/blob/rust-v0.156.1/codex-rs/core/src/tools/mod.rs#L72)
and [disabled-host provider](https://github.com/openai/codex/blob/rust-v0.156.1/codex-rs/code-mode/src/remote_session.rs#L87).

The version 2 implementation requires:

```toml
features.code_mode_host = { enabled = true, disable_in_process_fallback = true }
features.code_mode = false
```

It verifies both effective configuration values and the enabled feature flag.
The selection version and discovery identifier change together; a v1 discovery
does not satisfy v2 mediation checks. The v1 parameter schema and exact method
string remain supported for historical projection. Existing thread/turn identity,
duplicate-call, pre-inference stop and InvocationFiles checks remain unchanged.
Native continuation still requires an exact backend selection match; a v1 call
is not silently continued under the v2 policy.

This enables the native computation bridge. The pinned implementation creates a
[plain V8 context](https://github.com/openai/codex/blob/rust-v0.156.1/codex-rs/code-mode-runtime/src/runtime/mod.rs#L181)
with [explicit globals](https://github.com/openai/codex/blob/rust-v0.156.1/codex-rs/code-mode-runtime/src/runtime/globals.rs#L15).
It does not install Node, Deno, filesystem, process or fetch APIs, and
[rejects module imports](https://github.com/openai/codex/blob/rust-v0.156.1/codex-rs/code-mode-runtime/src/runtime/module_loader.rs#L225).
Tools route through the native broker to the existing item/tool/call boundary.
The adapter still admits only ymp_read/ymp_write callbacks through the original
file mediator. Empty environments, shell denial, disabled external services and
network=false are retained. Native pure clock/plan helpers may exist; ALL_TOOLS
is not claimed to contain exactly two entries.

The host uses its own process group. Upstream disconnect handling cancels active
cells, shuts sessions down with bounded waits and terminates V8 execution. This
source-level cleanup does not prove financial cessation or relax scoped file
withdrawal. A cell can outlive a turn, so stale callbacks must continue to fail
the exact invocation/turn and file-authority checks.

A zero-inference probe of installed 0.156.1 confirmed the required host table,
other effective guards, zero environments/roots/instruction sources and
networkAccess=false. The bundled codex-code-mode-host is a regular executable
beside the canonical standalone codex binary (mode 0755), with the package
manifest present and no preferred codex-resources helper. This is static
availability evidence, not proof of native tool execution. The actual Rust
metadata-only consumer passed in 2.17 seconds with seven offerings and zero
model turns. Three protocol-consumer scenarios passed in 6.76 seconds, including
refusal of an effectively disabled host and an enabled in-process fallback.
The final three protocol cases, including v1/v2 attribution, passed in 6.25
seconds. A focused filesystem check verifies resource-before-bin selection,
refusal of a non-executable preferred helper and missing-helper refusal.

Native discovery and start now check the helper actually selected by the pinned
installation layout. Recognized package bin, resources and CodexCLI.app layouts
follow the native precedence. Ambiguous non-package legacy resource layouts are
explicitly unavailable, rather than guessed from ambient CODEX_HOME or package
manager settings. ProtocolFixture remains distinct and does not claim an
installed helper. File presence and execute bits are static prerequisites, not
proof that a future spawn succeeds. The actual native metadata consumer passed
again after this guard in 1.83 seconds, with zero model turns. Independent review
accepted the final source (R1, 9/10). Full make verify passed, including all nine
Dispatcher scenarios in 139.51 seconds. Native file-tool execution under version 2
was not established by those checks. A later
[run 07](experiments/homogeneous-gpt-elementary/run-07.json) actually read the
input through ymp_read under v2. The returned bytes and successful native dynamic
tool item are retained. It also exposed a coverage limitation: commentary and a
file callback can belong to one response before its shared token update, whereas
the current pending_usage guard marks that batch as a gap. The receipt remained
Partial and its financial hold is preserved. A grouping repair is under
investigation; native writing and complete producer/reviewer delivery remain
unverified.
