**P1 — The first catalog migration disconnects qualified experience for an already concrete pinned or defaulted execution.** In `ymp-rust/crates/ymp-providers/src/discovery/catalog.rs:203`, migration resolves the existing execution policy and then unconditionally copies its model into `AgentProfile.model` at line 213. A generated legacy profile can already request a concrete model through `execution.fixed.model` or `execution.defaults.model` while its raw profile model is `None`. Migration changes that raw field without changing the effective execution. `AgentProfile::version` hashes the raw field (`ymp-rust/crates/ymp-core/src/config.rs:58`), and `execution_config_version` embeds that profile version (`ymp-rust/crates/ymp-core/src/config/execution.rs:113`). Runtime allocation uses the resulting key to locate the effective execution version and its reputation (`ymp-rust/crates/ymp-runtime/src/engine/allocation.rs:350`). Existing evidence remains stored, but subsequent identical execution no longer finds its qualified experience through the same key.

The reviewer reproduced this through the frozen executable and public core APIs in an isolated temporary application home, using the repository's scripted Codex metadata fixture. Start with actor `codex`, profile model `None`, fixed model `wire-a`, and fixed effort `quiet`; call `ymp catalog --refresh --timeout-secs 5`; reload the configuration. Actor ID, instructions, provider, effective requested settings, supplied reported settings, and supplied native version are unchanged. Only profile model changes to `Some("wire-a")`. The public execution-version function returned:

```text

same_requested_settings=true
```

The exact digests include temporary fixture paths; the demonstrated inequality is the invariant failure. The existing repeat-scan test takes its initial version after the first migration, so it cannot detect this regression. Preserve execution identity when a scan merely materializes an already effective explicit model. Add first-migration coverage for both fixed and defaulted model policies, with an existing qualified-experience lookup before and after migration. A genuinely changed or previously unknown execution may remain a distinct version; historical records must not be rewritten to conceal the mismatch.

## R4 — Configuration and scan lock lifecycle accepted

Reviewed commit: `54153929584d849866e95a7695d432d227a03914`. Review date: 2026-09-13. Verdict: **accept the bounded lock-lifecycle correction**, score **9/10**. The R3 integration finding recorded in `native-catalog-configuration-lock-finding.md` is closed for this candidate. R1/R2 remain historical review records; their native naming and execution-identity conclusions remain applicable. No blocker was found in the R4 scope. Integration into the current main executable and the supported owner-home refresh remain the parent's separate acceptance steps.

The production delta introduces private `ConfigurationLock` and `CatalogScanLock` guards that call `fs2::FileExt::unlock` in `Drop` before their file handles close. Both guards are constructed only after successful acquisition. Configuration ownership covers both ordinary save and scan publication, including the concurrent-edit check; scan ownership covers discovery, reconciliation, publication, and cancellation/error returns. The guard fields are private, the guards are not cloneable, and the change neither removes lock files nor weakens exclusive acquisition. There are no retry sleeps masking a delayed release.

Both deterministic Unix controls duplicate the original owner's file descriptor, prove that a live owner excludes another operation, drop that owner, and acquire a replacement while the duplicated old descriptor remains open. They then prove that closing the old descriptor cannot release the replacement owner's lock, and that ordinary save/refresh resumes after the replacement owner ends. This models the shared open-file-description lifetime directly without relying on fork timing. The two reviewed close-only controls fail precisely at immediate replacement acquisition. The original integration failure did not identify its particular retaining child; this review confirms the demonstrated lifecycle mechanism without claiming that missing process evidence.
