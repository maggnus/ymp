# Evaluation plan and findings

Use this same document before and after execution. Replace the instructional
sentences with the actual case; omit inapplicable detail with a stated reason.
The common protocol defines semantics. This template defines no fixed model,
budget, browser, task, platform, repetition count or publication requirement.

## Decision and scope

- Evaluation name, task-register link and accountable owner.
- User/product question and the decision the result will inform.
- Mode: regression, integration/release, diagnostic, comparative, experience,
  UX or reliability.
- Exact goal, inputs and expected deliverables/behavior.
- Primary endpoint and required acceptance layers.
- Current status of execution, product outcome and analytical completion,
  recorded separately.
- Applicable intent goals and principles; explain limits on evaluating the rest.

## Baseline and authority

Record source/executable/platform versions, relevant native identities and
settings, policy versions, knowledge/reputation/native context state, existing
evidence, fixed conditions and the intentional change. List confounders.

Record existing authorization for the selected actions, resource policy and
stopping/continuation rule. Keep development/review work separate from measured
runtime work. State whether external publication is part of this assignment.
Inventory prior reachable artifacts before repeated runs; specify preservation
and contamination checks appropriate to actual permissions.

## Hypotheses and criteria

For each selected question state the causal mechanism, plausible alternative and
observation that would falsify it. A comparison also needs its unit of analysis,
controls, treatment order, task selection, resource basis and uncertainty method.
Exploratory observations must not replace a failed primary endpoint afterward.

| ID / intent link | Required, conditional or exploratory | Requirement / hypothesis | Expected result or transition | Evidence method / counter-explanation | Verdict and evidence after execution |
| --- | --- | --- | --- | --- | --- |
| | | | | | |

For a full run include artifact and native completion separately. For a focused
test state its expected accepted or rejected behavior. Bind checks/reviews to
the result version they assess. Record whether each assertion is discriminating,
inspection-only, non-discriminating or absent; do not equate exit 0 with quality.

## Execution and observations

Describe the smallest sufficient sequence and domain validator. Define observation
boundaries, which failures stop or continue the test, and how evidence is retained.
Choose expected behavior before seeing the result; adapt only implementation-
specific selectors or equivalent observation details afterward.

| Attempt / source | Start/end and terminal state | Artifact/check evidence | Resources and coverage | Intervention / contamination | Outcome |
| --- | --- | --- | --- | --- | --- |
| | | | | | |

List observer actions separately: preparation, advice to participants, manual
changes, approvals, restart, independent verification, publication and analysis.
Report unknown active-human time as unknown. Preserve failed attempts rather than
replacing them with the later successful run.

Explain what the user received, whether status was truthful, what useful
cooperation occurred, where time/resources were spent, and which remedies were
available. Show why each material interpretation is stronger than its rival.
Do not invent a combined score or causal benefit unsupported by the design.

## Findings and proposals

| Priority / user impact | Fact and causal chain | Rival explanation | Proposed before/after behavior | Subsystem / tradeoff / rejected alternative | Smallest discriminating next check |

Separate defects, missing product capabilities, research hypotheses and optional
improvements. A proposal is not implemented behavior and does not authorize a
new experiment. Record strengths as well as failures and superficial symptoms.

## Verdict and reusable lessons

State acceptance for each required layer, overall outcome, remaining gaps and
the next justified decision. If the objective remains unmet, keep that explicit
even when observation and reporting are complete. Identify any general lesson
worth updating in the project skill; keep incidental case details out of it.
